# 記帳流程優化：實作與驗證計畫

基準：`origin/main` 87e915703f5d38d36d666b1f4489436d3a5d19b3。現有 67 個直接相關單元測試通過。

## 契約

1. 新帳目幣別依目的地建議；旅程可明確覆寫預設。只影響之後新開表單，不改歷史或已開草稿。
2. 新帳目日期若本地今天在旅程日期範圍內，預設當日 Day；否則沿用目前行程日。編輯與複製保留原日。
3. 實際付款可由多位旅伴分攤，輸入每位實付的台幣金額。實付合計必須與帳目折合台幣總額一致，結算按各人實付抵扣各人應分攤。舊單人帳目繼續由 `payer` 表示全部實付。
4. 自訂分帳可從每人固定台幣金額反推總額；外幣按目前匯率顯示相應當地金額，儲存前仍須通過既有金額守恆檢查。
5. 增加娛樂分類，保留其他作未知分類的後備。
6. 大量帳目按日期收合；摘要保留日期、筆數、合計，可鍵盤展開，仍能看到每筆詳情並編輯。

## 順序

1. 先加 helper／計算與表單失敗測試，再實作至通過。
2. 加明細收合與分類測試，再實作。
3. 跑直接相關單元與 Playwright，查任何回歸。
4. 執行 `npm run verify:fast`、`git diff --check`，審查 diff。
5. 提交並建立 Draft PR，等待最新 head 的 CI 結果；不合併、不部署。

## 邊界與風險

不改 Firebase Rules、repository API、已存在的金額／分帳精度與結算匹配算法。新增的多付款欄位須有精確單元／E2E 回歸；舊資料不批次遷移。分類與預設幣別是局部 metadata 與表單變更。

## 實作決策與驗收紀錄

- 「固定比例」依現有自訂分帳介面解讀為每人固定台幣金額：填入後以目前匯率反推當地總額；使用者仍能手動修正當地金額，最終儲存仍走原有分帳驗證。
- 多付款人輸入的是各人實際支付的台幣金額，與「誰負擔」的分帳欄位分開。`payments` 只用於多人付款的新紀錄；既有單人紀錄保留原 `payer` 契約，沒有批次遷移。兩種總和在表單提交時各自驗證。
- 目的地只做現有六種幣別的關鍵字建議；複合旅程與無法辨識的地名可使用旅程覆寫。硬編碼匯率是原有可編輯的初始值，並非即時報價。
- 帳目超過 20 筆時，預設展開最後一個有帳目的日期；每個日期先顯示最新 10 筆，可展開較早帳目。少量帳目保持原先全部可見。
- 歷史帳目缺少幣別時仍按台幣編輯；更改預設幣別只改旅程 metadata，不改既有帳目。多人付款旅伴失效時要求重新分配實付與分帳。
